# sqlalchemy — held at 2.0.36 after evaluating a bump, not by inertia.
#
# The A2A Compliance Report of 2026-08-27 flags this component under
# sonatype-2021-0025 (7.5 High, SQL injection via dynamically-assembled SQL).
# An upgrade was tested against 2.0.52 and is compatible: the backend suite
# passes unchanged. It was NOT applied, for two independent reasons.
#
# 1. IT WOULD NOT CLEAR THE FINDING. sonatype-2021-0025 was published in 2021
#    and fires against 2.0.36, released three years later. It is a
#    Sonatype-proprietary advisory describing a CAPABILITY of the library —
#    that text()/execute() will run whatever string you hand them — rather than
#    a defect in any release. No version removes that capability, so no version
#    clears the advisory. The scan report itself lists no fixed version and no
#    recommended upgrade. What closes it is not building SQL from strings, which
#    is enforced by backend/tests/test_no_dynamic_sql.py and recorded in
#    security/vex/partner-platform.vex.json.
#
# 2. IT WOULD DEEPEN AN EXISTING BUILD DEFECT. requirements.lock is already
#    stale (see backend/tests/test_requirements_lock_sync.py), and it cannot be
#    regenerated without registry access and a container runtime. Editing this
#    pin alone would add a fourth version skew between the file production
#    installs and the file CI installs, for no security benefit.
#
# Bump this when there is a finding a bump actually resolves, and regenerate
# the lock in the same change.
sqlalchemy==2.0.36
httpx==0.28.1

# JWT: PyJWT, replacing python-jose (2026-08-20) — bumped in lockstep with
# backend/requirements.txt, which carries the full rationale. Short version:
# python-jose declares `ecdsa` as an unconditional core dependency, and ecdsa
# carries CVE-2024-23342 (HIGH) with no fix in existence, so the library had to
# be removed rather than pinned around. PyJWT has zero required dependencies and
# no ecdsa. 2.13.0 is the first PyJWT release with no advisories of its own.
#
# The `[cryptography]` extra is intentionally NOT carried over as a PyJWT
# extra: PyJWT only needs it for RS*/ES* algorithms, and this platform is
# HS256-only. `cryptography` is nevertheless a direct, declared dependency of
# this service now — see the explicit pin below.
PyJWT==2.13.0
# cryptography — a DIRECT dependency as of the secrets-at-rest work:
# `app/core/secret_box.py` uses Fernet (`cryptography.fernet`) to encrypt
# provider keys and A2A secrets stored in `partner_settings.value`. This is the
# SAME mechanism and the same `enc:v1:` token format the NPCI backend already
# runs in production (core/app_config_sync.py, core/encrypted_type.py), so the
# two services finally agree on one scheme rather than each carrying its own.
# It previously arrived only transitively via google-auth, which is not a
# contract to rely on — a transitive dep can be dropped by an upstream release
# and would take secret decryption with it. Pinned to match the NPCI backend so
# both resolve the same version. See docs/adr/ADR-0002-secrets-vault-migration.md.
cryptography==50.0.0
